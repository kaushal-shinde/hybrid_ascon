# NIST Lightweight Cryptography finalists — reference C

The nine algorithms that competed against Ascon in the final round of NIST's
Lightweight Cryptography Standardization Process, alongside Ascon itself
(already vendored as `../ascon-aead128/`). Ascon won; these nine did not.

## Source

Each directory is the **reference (`ref`) AEAD implementation** from that
algorithm's official final-round submission package, downloaded from NIST:

`https://csrc.nist.gov/CSRC/media/Projects/lightweight-cryptography/documents/finalist-round/updated-submissions/<name>.zip`

Fetched 2026-08-28. Finalist list and package links per
[csrc.nist.gov/Projects/lightweight-cryptography/finalists](https://csrc.nist.gov/Projects/lightweight-cryptography/finalists).

| directory | algorithm | primary AEAD variant taken |
|---|---|---|
| `elephant/` | Elephant (Dumbo) | `elephant160v2` |
| `gift-cofb/` | GIFT-COFB | `giftcofb128v1` |
| `grain-128aead/` | Grain-128AEAD | `grain128aeadv2` |
| `isap/` | ISAP (ISAP-A-128A) | `isapa128av20` |
| `photon-beetle/` | PHOTON-Beetle | `photonbeetleaead128rate128v1` |
| `romulus/` | Romulus (Romulus-N) | `romulusn` |
| `sparkle/` | SPARKLE (Schwaemm256-128) | `schwaemm256128v2` |
| `tinyjambu/` | TinyJAMBU-128 | `tinyjambu128v2` |
| `xoodyak/` | Xoodyak | `xoodyakround3` |

Each submission offers several variants (different key/tag sizes, different
permutation widths); the table above is each team's stated **primary** or
recommended variant. Only that one is vendored per algorithm — see
"Not vendored" below.

`crypto_aead.h` is the shared eBACS prototype header the reference sources
include; taken from the PHOTON-Beetle package, semantically identical to the
one already vendored at `../ascon-aead128/crypto_aead.h` (same two prototypes,
different formatting).

## No official hardware

**None of the nine submission packages contains a single `.v` or `.vhd` file.**
NIST's final-round packages are C only. Hardware is not part of what NIST
published; each submitting team may or may not publish HDL separately, under
their own terms, of varying language and completeness. None is vendored here.
`../verilog/` remains the only RTL in this project.

## Verification

Each implementation was compiled and checked against the **official KAT
vectors shipped inside its own submission package** (not generated by this
project): 1089 encrypt + 1089 decrypt vectors per algorithm, 9801 each way,
all passing exactly. A round-trip and tag-tamper-rejection smoke test (147
message/AD-length combinations per algorithm) also passed for all nine.

## Licensing

NIST's call for submissions required each submitter to grant royalty-free
rights to practice the submission for the purposes of the standardization
process, as a condition of the submission package rather than a per-file
licence header — most of these `.c` files carry no in-source licence
statement. Two exceptions state their own terms in-file: SPARKLE credits its
author group under the NIST submission; Xoodyak's implementation is
public-domain (CC0-style waiver). Consult each package's `Documents/` and the
NIST call for submissions before any use beyond study and benchmarking.

## Not vendored

- Every non-primary variant of each algorithm (Elephant's other two sizes,
  ISAP's five other modes, Romulus's six other members, SPARKLE's three other
  members, TinyJAMBU's two other key sizes) — ~23 further `ref` directories
  across the nine packages.
- Hash-only modes (ISAP, Xoodyak, and others offer one).
- `genkat_aead.c`/testbench drivers, `Documents/`, and every non-`ref`
  optimised implementation (ARM, AVR, x86 assembly, masked variants) in each
  package.
