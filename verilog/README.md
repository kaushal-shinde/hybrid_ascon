# Verilog: Ascon-AEAD128, the two hybrids, and the 9 NIST LWC finalists

Twelve hardware AEAD cores in one directory: Ascon-AEAD128, the two
Ascon-SipHash hybrids (`../ascon-siphash/`), and one core per algorithm that
lost to Ascon in the final round of NIST's Lightweight Cryptography
competition (`../lwc-finalists/`). All twelve are measured together in
`../RESULTS.md` — this is one comparison, not two.

`ascon_aead128.v`, `asconsip_aead.v` and `asconsip64_aead.v` are functional
twins of the C in `../ascon-aead128/` and `../ascon-siphash/`. The other nine
are transliterations of the reference C vendored in `../lwc-finalists/`,
whose own `PROVENANCE.md` records where and when each was fetched from NIST.
The two hybrids are unanalysed constructions — see `../ascon-siphash/README.md`.

## Two interfaces, one comparison

These twelve cores were not all built to the same port convention, and
merging them into one directory doesn't erase that — it's a real fact about
how they were built, not filing:

- **`ascon_aead128.v`, `asconsip_aead.v`, `asconsip64_aead.v`** share a
  **custom** block-oriented interface (documented in full at the top of
  `ascon_aead128.v`): a one-cycle `start` pulse with `key`/`npub` held valid,
  then associated-data blocks (`din_ad = 1`) followed by message blocks
  (`din_ad = 0`), each phase terminated by a block with `din_last = 1` and
  `din_bytes` giving its real length. Decrypt is latched from `decrypt` at
  `start`; the core emits its computed tag on `dout`/`tag`.
- **The other nine** all implement the **NIST LWC Hardware API** (GMU CERG
  PDI/SDI/DO word-stream protocol — the same convention the real NIST
  hardware competition used to benchmark every finalist, Ascon included):
  32-bit `valid`/`ready` word streams, instruction opcodes
  (`ENC`/`DEC`/`LDKEY`/`ACTKEY`), and 32-bit segment headers (type,
  partial/eoi/eot/last flags, 16-bit length).

**The two are not interchangeable or directly comparable at the port
level** — only at the algorithm level (area, timing, power — see
`../RESULTS.md`). Each file's header states which interface it uses.

All twelve cores in this directory now pass a KAT-style vector suite in
simulation: `ascon_aead128.v` and all nine finalists (ten of twelve) against
the official NIST test vector suite for their own algorithm, and the two
hybrids against a self-generated KAT vector suite from their own reference C
(no official NIST suite exists for either — see below for exactly what that
distinction means and why it matters) — nothing here is
lint-clean-but-unconfirmed any more. Getting there took finding and fixing
42 real bugs across eight of the nine finalist cores (tallied below;
`tinyjambu_lwc.v` was already KAT-verified going into this pass), none of
them caught by linting or by hand review beforehand; each file's own header
still names the exact reference source it was transliterated from and
documents every non-obvious design decision made along the way (byte-order
conventions, padding edge cases, capacity limits where relevant), now
alongside the specific bugs the KAT run against that source turned up.

**Ascon-AEAD128's KAT run.** `ascon_aead128.v` implements NIST SP 800-232
itself, so an official-format KAT vector suite exists for it:
`LWC_AEAD_KAT_128_128.txt`, 1089 `Count`/`Key`/`Nonce`/`PT`/`AD`/`CT`
vectors (every combination of 0..32-byte plaintext and 0..32-byte
associated data, the standard NIST LWC KAT grid), generated from NIST's own
vendored `ascon-c` reference implementation for exactly this algorithm —
key/nonce/tag 16/16/16 bytes, matching this file's own header. A testbench
adapted from the existing 16×16-grid `xsim/tb_ascon.v` (same custom block
protocol, same driver logic, same fixed key/nonce the KAT suite itself
uses — only the stimulus source and vector count changed) walked all 1089
vectors through `ascon_aead128.v`'s real interface in Vivado `xsim`, both
directions: **1089/1089 encrypt, 1089/1089 decrypt**, run 2026-09-02 against
the same unmodified RTL measured throughout `../RESULTS.md`. No bugs were
found or fixed — this run confirms correctness, it doesn't change the RTL.

**Why no *official* KAT vector suite exists for the two hybrids.**
`asconsip_aead.v` and `asconsip64_aead.v` implement experimental
Ascon-SipHash constructions that are not a NIST submission (see
`../ascon-siphash/README.md`: "unanalysed constructions — no cryptanalysis
has been done on either"), so there is no NIST-published set of
Count/Key/Nonce/PT/AD/CT vectors for an algorithm NIST never received. The
repository does vendor the standalone SipHash reference (`../siphash/`),
whose own README describes a standard 64-vector KAT for SipHash-2-4 — but
that source drop doesn't actually include the vectors or the `test.c` that
checks them, only the round-function source and constant-round headers; and
even if it did, those vectors exercise SipHash-2-4's own keyed-PRF/MAC
construction, not the duplex-sponge AEAD construction `asconsip_aead.v` and
`asconsip64_aead.v` build around SIPROUND (different absorption/squeeze
schedule, different round-constant injection, different padding) — passing
them would say nothing about the AEAD cores. There being no official suite
to run against doesn't mean nothing more rigorous than the 16×16 grid could
be done, though — see below for what was actually done about it.

**The two hybrids' self-generated KAT run.** NIST's own KAT-generator
program, `genkat_aead.c` (vendored unmodified in the `ascon-c` reference
tree, the same file used verbatim to produce `LWC_AEAD_KAT_128_128.txt` for
`ascon_aead128.v` above), is algorithm-agnostic: it only calls
`crypto_aead_encrypt`/`crypto_aead_decrypt` through `crypto_aead.h` and
reads `CRYPTO_KEYBYTES`/`CRYPTO_NPUBBYTES`/`CRYPTO_ABYTES`/`CRYPTO_NSECBYTES`
from `api.h`, then sweeps the standard 0..32-byte PT × 0..32-byte AD grid
(1089 vectors) with NIST's own incrementing key/nonce convention. Neither
hybrid ships an `api.h` of its own (`../software/bench/build.sh` instead
compiles them with explicit `-DKEYBYTES=16 -DNPUBBYTES=16 -DABYTES=16`), so
a small `api.h` (16/16/16, matching the table above) and a `crypto_aead.h`
shim (`#include`s the hybrid's own header, then `#define`s
`crypto_aead_encrypt`/`crypto_aead_decrypt` to
`asconsip_aead_encrypt`/`_decrypt` or `asconsip64_aead_encrypt`/`_decrypt`)
were written to redirect the generator's unmodified calls at each hybrid's
own reference C — `../ascon-siphash/asconsip.c` / `asconsip64.c` — instead
of Ascon's. This produced two real KAT files, 1089
`Count`/`Key`/`Nonce`/`PT`/`AD`/`CT` vectors each, in the exact format
`LWC_AEAD_KAT_128_128.txt` uses, whose *answers* come from that hybrid's own
correct reference implementation — genuinely computed, not copied from
Ascon's (which computes a different function and would produce meaningless
mismatches if reused directly) or from anywhere else. A testbench adapted
from `kat_ascon/tb_ascon_kat.v` (same custom block protocol, same driver
logic, same fixed key/nonce convention the generator itself uses — r=64's
copy narrowed only to its 8-byte block / 64-bit `din`, per r=64's own header)
walked both files through `asconsip_aead.v` / `asconsip64_aead.v`'s real
interface in Vivado `xsim`, both directions: **1089/1089 encrypt, 1089/1089
decrypt for r=128; 1089/1089 encrypt, 1089/1089 decrypt for r=64**, run
2026-09-04 against the same unmodified RTL measured throughout
`../RESULTS.md`. No bugs were found or fixed — like Ascon-AEAD128's KAT run,
this run confirms correctness, it doesn't change the RTL.

**Read this precisely: it is real KAT-style verification, but it is not the
same claim as "passes the official NIST KAT suite."** The vectors are real
(genuinely computed by re-running NIST's own generator program against each
hybrid's own reference C, not fabricated or hand-picked) and the coverage is
real (the same 1089-vector 0..32-byte PT×AD grid every official NIST LWC KAT
file uses, not a smaller or easier one) — this is a materially stronger
check than the original 16×16 grid, which both hybrids also still pass. But
NIST never evaluated these constructions, so there is no independent,
NIST-published answer key anywhere to check the reference C itself against;
the vectors' correctness rests entirely on `asconsip.c`/`asconsip64.c` being
right, the same reference the RTL and the 16×16 grid were already being
checked against. What this run adds is a second, independent path (the
generator program plus a much larger vector set) confirming the RTL agrees
with that same reference — it does not, and cannot, independently confirm
the reference itself is correct the way an official NIST suite would for a
NIST-evaluated algorithm.

**What KAT simulation actually catches, illustrated by `xoodyak_lwc.v` and
`giftcofb_lwc.v`:** lint-clean and even a clean single-transaction
simulation missed every one of the 15 real bugs these two cores turned up —
full-grid KAT simulation (1089 message/AD-length combinations, both
directions) was needed to surface each one. Xoodyak (6): `pdi_ready`
asserted one cycle too early on an empty AD/PT chunk (silently ate the next
segment's header word — invisible on any AD/PT length that isn't exactly a
multiple of the rate); two missing domain-separation bytes (`Cu=0x80`,
`Cu=0x40`) documented in the file's own header comment but never wired into
the RTL; `do_valid` wrongly asserted during decrypt's internal tag
recomputation (a growing word-count drift, invisible on any single
transaction in isolation); an encrypt/decrypt state-absorption asymmetry
that happened to cancel out correctly on every all-empty test case and only
diverged once a KAT record with real plaintext exercised it; and one
Vivado `xsim`-specific scheduling bug where calling the same non-automatic
function twice in one expression inside a `for` loop silently corrupted the
result. GIFT-COFB (9): the same `pdi_ready`-too-early and `do_valid`
-during-decrypt bug classes recurring independently; a systemic byte-order
mismatch between the LWC bus's little-endian words and GIFT-128's own
big-endian internal state (right byte *group*, wrong order within it —
correct-looking on every KAT record only by coincidence of the test
pattern, until compared word-for-word against the C reference); a
partiality test that checked the wrong bits (`chunk_len[1:0]`, a word-count
remainder, where the reference's `alen%16!=0` needed testing against a full
16-byte block, not a 4-byte word); a GIFT-128 key schedule silently reused
without being reset between cipher calls (the reference re-derives it fresh
every call, since the schedule itself mutates each of the 40 rounds); a
double-vs-quadruple offset bug from reading a "double the offset" wire a
cycle after the offset register it depends on had already been doubled; a
DO-word count that didn't shrink for a short final chunk (always emitted 4
words regardless of chunk length); and the same encrypt/decrypt
absorption-asymmetry bug class as Xoodyak's, independently. Grain-128AEAD
(5, 2 of them the same `pdi_ready`/`do_valid` bug classes checked for and
fixed proactively before running): a live combinational wire re-evaluated
with a *different* keystream bit during the MAC phase than the one that
actually produced the output bit, so encrypt (whose MAC formula never
reads the keystream at all) was unaffected while decrypt's MAC silently
diverged from a matching encrypt's, despite recovering the correct
plaintext; and an output word register never cleared between words, so a
final output word shorter than 4 bytes leaked the *previous* word's
leftover upper bytes instead of the zeros the API's Sec. 2.7 requires.
Romulus (3): a systemic byte-order mismatch between the LWC bus's
little-endian words and the file's own (incorrect) header claim that no
swap was needed — six load/output sites (`key_r`, `npub_r`, three AD/PT
block loads, the DO/tag word mux) needed a `bswap32`, a class of bug a
linter cannot catch because a wrong assumption stated in a comment reads
exactly like a correct one; a block-assembly register (`blk_in`) built as a 4-word shift-in,
correct only when a block is exactly 16 bytes — any shorter AD or message
block (the common case) landed its word(s) at the bottom of the register
instead of top-aligned at byte 0, and since the register is only cleared
on global reset (not per block), the unused high bytes carried over stale
content from whatever the *previous* block had left there, rather than
being predictably zero; and the same Sec. 2.7 output-clearing bug as
Grain-128AEAD's, independently — a short final ciphertext/plaintext word
computed `keystream ^ stale-byte` for its unused byte lanes instead of the
zero the reference `rho`/`irho` explicitly write. The `blk_in` bug is the
most instructive of the three: it passed every KAT record whose AD and
message were empty or an exact multiple of 16 bytes, and only the 66th
transaction (a 1-byte message) into the 2178-transaction grid exposed
it — nowhere near a corner a hand review would have singled out.
SPARKLE (1): the exact opposite documentation error from Romulus's — its
header correctly recognised that the reference's word-domain arithmetic
needs the bus and the C to agree on byte order, but concluded (wrongly)
that the bus packs bytes big-endian per word and added a compensating
`bswap()` at all nine load/store/compare sites; the bus in fact already
matches the reference's own little-endian-per-word view directly, so
every one of those nine swaps was actively wrong, and simulation caught
it on the very first, simplest KAT record (empty AD, empty message) since
the corruption was in nonce/key loading, not in any AD/PT edge case.
PHOTON-Beetle (9, 3 proactive): the same byte-order, `blk_in`
top-alignment/stale-content, and Sec. 2.7 output-clearing classes checked
for and fixed proactively before the first run, plus six found only by
the KAT grid -- a round-constant table indexed `row*12+round` (documented
in its own header) but called with a bit-concatenation that computes
`row*16+round` instead, silently correct only for row 0; a classic
Verilog non-blocking-assignment hazard where the state's initial
Npub||Key concatenation read the nonce register's OLD value on the very
same cycle its 4th and final word was being written into it, silently
dropping that word; the PHOTON256 permutation's nibble-repacking step
writing every nibble to the opposite half of its byte from where it was
unpacked; a second Vivado `xsim` inline-function-call corruption (the same
class as xoodyak_lwc.v's, here on a GF(2^4) multiply called 64 times in a
tight loop, driving an entire permutation round to all-zero -- found by
building an isolated single-round testbench and a matching ground-truth
probe against the reference's own `AddKey`/`SubCell`/`ShiftRow`/
`MixColumn`, comparing stage by stage until the exact operation
diverged); the AD/message absorption XORing into the wrong 128-bit half
of the 256-bit state (the capacity instead of the rate the reference
actually absorbs into, plus a redundant second copy of the mask's last
byte landing in yet another wrong location) -- invisible on the
empty-AD/empty-message record, since that path never reaches the
absorption code at all, and caught by the very next KAT record; and a
1-bit rotate implemented as eight independent per-byte rotates instead of
one rotate across the whole 8-byte value, correct only when a byte's own
low bit happened to equal its successor's, which took 301 KAT records
before a message finally exercised a byte pair that differed.
Elephant (5): a byte-order confusion touching key/nonce/message loading,
the AD byte array, and both output words, but taking three different
buggy forms rather than one -- register loads applied a spurious byte
swap despite the file's own header already correctly stating the target
convention needed none of the bus's own per-word layout; the AD byte
array had its four per-word byte lanes wired to reversed indices; and
both output-word constructions placed the first byte at the wrong end of
the bus word, the mirror image of the register-load mistake; a bit-
reversal helper (`retnuoCl`) whose last term was a literal 0 instead of
the input's top bit, dropping it silently for as long as the evolving
round-counter LFSR's top bit stayed 0, which it does not for all of the
80 rounds in every permutation call; a companion LFSR step
(`lcounter`) with its single feedback bit wired one position to the left
of where the reference ORs it in; and, the most interesting of the five,
a tag computation that fed the wrong buffer into the running hash on
decrypt -- the reference's own `get_c_block` call site reads a formal
parameter that is bound differently by its two callers (`encrypt`
vs. `decrypt`), and encrypt's binding makes it read the ciphertext being
produced while decrypt's makes it read the ciphertext being consumed
(not, as the natural-seeming reading and this file's original header
comment both assumed, the plaintext just recovered); this produced
correct plaintext and correct ciphertext on every single-block message
but a wrong tag on every decrypt, traced only by writing a debug build of
the reference C itself and printing which pointer each branch actually
dereferenced.
ISAP (4), the last of the nine finalists to reach KAT: the third
occurrence in this directory of the exact same false "the bus already
matches the reference's byte order, so no swap is needed" claim as
romulus_n_lwc.v and photonbeetle_lwc.v, this time needing a `bswap32` at
every load, output and comparison site; the same nonce-register timing
hazard as photonbeetle_lwc.v's, independently, in ISAP's own MAC-init
state load; a genuine deadlock, not a wrong answer -- deriving the
encryption sub-key unconditionally fell through into a state that waits
for a plaintext-data bus word, which an empty message never sends, hanging
every empty-message transaction forever; and the most elusive of the
four, a byte counter (used to position the domain-separation and padding
bytes within the sponge's rate) that was reset only at specific
mid-transaction commit points rather than at the start of every
transaction, so a transaction whose own path reads it before reaching one
of those points -- any transaction with an empty AD -- silently inherited
whatever the *previous* transaction had left it at. That previous-value
leak was invisible for the first 66 transactions of the KAT grid, because
every one of them happened to already have the counter sitting at 0 (all
their preceding transactions had empty AD or empty messages too), and it
took a genuinely three-way pattern -- record 33 has both a real,
albeit one-byte, message, and the record right after it has an empty AD,
which reads the not-yet-reset counter one transaction too early -- for the
bug to produce a wrong answer instead of a lucky one, found only by
comparing the same debug dump between a transaction's encrypt and decrypt
halves rather than against the reference at all, since both halves were
*equally* wrong until that comparison singled out which state stopped
matching between them. None of these 42 bugs across eight cores were
contrived edge cases; nearly all were reachable within the first few
hundred transactions of the standard KAT grid.
